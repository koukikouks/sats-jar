# Bitcoin design: P2WSH jar, contract-built transactions, recovery to the child's wallet

> Amended by ADR 0009: the recovery branch of a re-homed jar is the child's own key from their recovery phrase, and "after unlock" below means after handover.

Decided by Claude, the proven standard way; none of it changes what users see beyond what ADR 0005 states.

- **Jar address (R1, R12):** a P2WSH script with two branches: (1) a signature from the jar's MPC-derived key, path = the jar's id; (2) after unlock plus two years (CLTV), a signature from the key behind the child's registered address (`DUP HASH160 <child key hash> EQUALVERIFY CHECKSIG`). So the Bitcoin-only exit needs no new secret: whoever holds the child's wallet can recover the jar if NEAR's signing network has stopped. The child's address must therefore be a native segwit `bc1q…`/`tb1q…` (P2WPKH) address from a wallet the parent controls, not an exchange deposit address. Taproot is ruled out because the MPC network cannot sign Schnorr (brief §6).
- **The contract builds every transaction itself (R3, O12).** It chooses the inputs from its own record of proven coins, sets the outputs (child's address, change back to the jar address), sets the fee, computes the BIP-143 sighash per input, and only then calls `sign`. No caller supplies a hash, an input amount or an output.
- **Only proven, confirmed coins (R6).** A top-up counts only after anyone submits a proof that the light client accepts with enough confirmations (ADR 0002). Coins below a dust floor are ignored. The jar's own change counts once its payment is proven confirmed the same way.
- **Anyone may trigger an allowance (O8, R7).** Because the contract decides payee, amount and inputs, a trigger can only ever produce a valid payment to the child; the app's keeper triggers it each period so it feels automatic.
- **Fees and stuck payments (R7, R9, O13).** The caller proposes a fee rate; the contract refuses one whose total fee would exceed the jar's fee cap. Anyone may replace a pending payment with the same inputs and outputs at a higher fee, up to the cap (RBF, as Omni's connector does). A replacement is the same payment, not a second one (R5).
- **No reuse (R8, O15).** Each input is reserved by exactly one pending payment until that payment is proven confirmed, and every signature is SIGHASH_ALL over the whole transaction, so signatures can't be recombined across payments. A signed payment is public in the NEAR receipt; anyone (normally the keeper) can broadcast it.
- **Inputs (O14).** At most 10 inputs per payment, largest first; the single change output consolidates the jar over time.
- **The jar's key (O16).** The contract derives each jar's public key itself from the MPC network's root public key, the same way Omni's connector does, and tests check it against the MPC contract's `derived_public_key` view.
- **After unlock (O18):** the holder may request any spend through the contract. The NFT cannot transfer while a payment it signed is pending, so a seller can't keep a pre-signed payment (pitfall 3); the holder can first replace it with a payment back to the jar.
- **Transfer re-homes the Bitcoin.** The recovery branch is fixed in the jar's address, so whoever holds the old recovery key keeps a claim on it. A transfer after unlock therefore moves every coin to a new jar address whose recovery branch is the new holder's registered address, and the NFT changes hands only once that move is proven confirmed. That is the answer to the track's "what stops the old owner from keeping access": the old owner's signatures and recovery key no longer touch any coin.
